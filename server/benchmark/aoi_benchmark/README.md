# AOI 空间索引方案压测选型

M2 阶段要做 AOI（兴趣区域）空间索引。在落地前，先用本目录下的独立压测程序对四种候选方案做横向对比，**以实测数据决定采用哪个方案**，而不是拍脑袋。

压测程序为纯内存原型，**不依赖**网关的 PG / Redis / gRPC，可独立编译运行。

## 一、四种候选方案

| 方案 | 数据结构 | 查询思路 |
|---|---|---|
| 十字链表 | X/Y 双排序结构 | 遍历 X 条带内所有 distinct x，按 Y 过滤 |
| 四叉树 | 动态树（叶子容量 16，超则分裂） | 递归下降 + 边界剪枝，精确距离过滤 |
| 固定九宫格 | `unordered_map<grid_id, unordered_set<uid>>` | O(1) 定位格子，扫周围 9 格 |
| 动态自适应九宫格 | 固定九宫格 + 热点格切分（阈值 200 → 50m 子格） | 扫 9 基格，被切分的格遍历其 4 子格 |

四种方案实现统一的 `AoiScheme` 接口（`insert / move / remove / query_near`），保证 AOI 语义可比。

## 二、编译与运行

```bash
# Windows bash（本机为 g++，建议开优化否则耗时数据失真）
g++ -O2 -std=c++20 aoi_benchmark.cpp -o aoi_benchmark.exe
./aoi_benchmark.exe
```

> 也可用 MSVC：`cl /EHsc /std:c++20 /O2 aoi_benchmark.cpp`

## 三、压测设计

| 参数 | 值 |
|---|---|
| 用户数 N | 10000 |
| 操作次数 M | 200000（每次 = 随机用户「移动 + 邻域查询」） |
| 地图 | 2000m × 2000m |
| 基础网格 | 100m |
| AOI 半径 | 150m（即 300m × 300m 邻域） |

- **两种密度分布**：均匀分布（用户散开）+ 聚集分布（80% 用户集中在 25% 面积的热点，模拟食堂/操场密度不均）。
- **四项指标**：邻域查询 avg / P99（核心）、移动更新 avg、广播范围（验证四者 AOI 语义一致）。
- 固定随机种子 `42`，结果可复现。

## 五、结论：采用固定九宫格

1. **查询最快且最稳**：两种分布下 avg / P99 均为四者最优。
2. **十字链表**最差，坐实「密度不均时退化」的淘汰判断。
3. **四叉树**排第二，有精确距离过滤、无越界广播，但查询比九宫格慢约 1.4×。
4. **动态自适应不值得引入**：查询反而慢 2.4×，切分带来的广播收益极小，是纯负收益。

## 六、原因分析

这个规模下拼的不是大 O，而是**常数因子**与**内存 Cache 友好度**（四种方案的复杂度都接近 O(邻居数)）。

**固定九宫格为什么快**：查询路径上没有任何多余动作——一次 floor 定位格子 + 9 次 hash 查找 + 顺序倒桶。不递归、不指针追逐、不做距离过滤，全部成本就是「把 9 个桶里的 uid 倒出来」。

**动态自适应为什么「增强反而慢」**（核心洞察）：
- 切分粒度（50m）**小于** AOI 半径（150m），切分改变不了「要广播给谁」，只改变「按多大粒度组织格子」。
- 粒度更细 → 同一 300m×300m 邻域，100m 格只需扫 3×3=9 格，切成 50m 子格后要扫 6×6=36 格，**扫描量反而 ×4**。
- 每次查询还要对 9 基格 × 4 子格 = 36 次 `find` 白探测（均匀分布下根本无子格，纯浪费），且对子格多做距离过滤。

**四叉树为什么第二**：指针追逐（递归访问子节点）+ 剪枝判断的常数开销，Cache 命中率低于顺序倒桶；聚集场景 P99 更高，印证树结构的长尾毛刺。

**十字链表为什么最差**：查询 = 遍历 X 条带内所有 distinct x（O(条带宽度)），聚集分布下 8000 人挤在热点里，300m 条带内 distinct x 数量暴增，性能严重退化。

### 数据口径说明（不影响结论）

- 固定九宫格广播范围（210.3 / 1805.6）略高于精确值（208.5 / 1738.6）：九宫格会把 9 格四个角落超出 150m 的用户也算进去，是网格方案的固有「假阳性」，工程上可接受。
- 动态自适应广播范围（180.0 / 1493.3）**低于**精确值，不是真收益，而是简化原型的一个 bug：切分后 base 格里「切分前已入格」的用户被漏扫（`query_near` 里 `split==true` 时跳过 `grid_[base]`）。
